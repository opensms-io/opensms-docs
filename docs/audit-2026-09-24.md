# Documentation UI and action audit, 2026-09-24

## Scope

This pass checked the documentation repository's static coverage and link
integrity without contacting the API or changing application state.

## Confirmed passing checks

The following commands were run from the repository root:

```text
node --test --test-name-pattern='every contract|no unredacted|key examples|intact tables' tests/reference.test.mjs
```

Result: 4 passing tests. This covers all 173 customer contract operations,
coverage rows, published example redaction, key response shapes, tables, and
internal links.

```text
node --test --test-name-pattern='developer pages: no em dashes' tests/developer.test.mjs
```

Result: 1 passing test. All getting-started and integration pages passed the
intro, relative-link, image, and typography checks.

## Initial static-only phase

The complete suite in `tests/run.mjs` includes live API replay, signup, key
creation, sender-ID document uploads, admin decisions, payment and webhook
flows. Those tests mutate workspaces, credentials, documents, and operator
state. They require a disposable API/database target and, for some admin
cases, dedicated operator credentials. They were not run against a shared
environment.

At the beginning of this audit there was no isolated target configured, so the
static-only phase intentionally stopped before live actions.

## Remaining evidence needed

- Finish the authenticated browser walkthrough against the isolated stack.
- Exercise every documented button, link, form submission, download, and
  preview action in that isolated environment.
- File GitHub issues only for failures reproduced in that environment.

## Isolated API-backed run

An isolated stack was available on 2026-09-24 with API `127.0.0.1:18180`,
PostgreSQL `15440`, Redis `16390`, and NATS `14230`. Outbound email, SMS,
webhook delivery, payments, and top-ups were disabled.

The complete `node tests/run.mjs` suite finished with 48 tests: 42 passed, 3
skipped, and 3 failures. The failures were:

- webhook event-envelope identity mismatch;
- rate-limit test did not observe a 429;
- `/healthz` returned 503 during the test's startup window.

The webhook test was rerun alone against the same stack and passed. The
rate-limit result was not promoted to a GitHub issue because it was not
independently reproduced and the run did not capture proof that enough requests
arrived inside the limiter window. The `/healthz` response was not captured
with headers and server logs at the failure point, so its cause is unconfirmed.

These are recorded as unconfirmed run observations, not product defects. A
fresh isolated stack with response capture and server logs is required before
filing an issue.

## Browser capture attempt

The Playwright capture script ran against the isolated UI at `127.0.0.1:5190`.
It captured signup, validation, email-verification, login, email-code,
forgot-password, reset-password, and wrong-password scenes. It then stopped at
the two-factor scene because the existing `kofi@opensms.test` account had 2FA
enabled but its secret was absent from the fresh state file. This is a fixture
state problem, not a confirmed UI defect.

A separate read-only route smoke checked `/`, `/login`, `/signup`,
`/forgot-password`, `/reset-password/example-token`,
`/login/code?email=test%40opensms.test`, and `/admin/login`. All returned 200,
rendered their expected headings, and produced no browser console or page
errors. Authenticated console routes remain pending because the documented test
account was not present and no mutating account creation was performed.

The capture runner was also attempted with a fresh API-created account state.
Its first onboarding scene redirected to `/login` after signup, so the expected
markets controls were not present. A direct messages-scene run likewise stayed
on `/login` and timed out before the compose phone input appeared. These runs
did not produce a confirmed UI defect because the account/session fixture was
not authenticated; they do establish that the browser walkthrough still needs
a known-good seeded session or an explicitly verified login handoff.

## Authenticated console run

After restarting the isolated API process and creating a fresh sandbox account,
the real browser login completed successfully. The legal gate accepted all
required documents, and these authenticated routes loaded without page errors:

`/app`, `/app/messages`, `/app/messages/new`, `/app/contacts`,
`/app/templates`, `/app/sender-ids`, `/app/numbers`, `/app/inbound`,
`/app/otp`, and `/app/settings/notifications`.

The compose scene exposed a reproducible validation defect: entering
`not-a-phone` and a non-empty message left the **Send message** button enabled.
The click did not produce an immediate client-side validation state and waited
on the request path. No SMS was sent because outbound delivery was disabled.
This is confirmed as a UI validation issue and was filed as
[frontend issue #146](https://github.com/opensms-io/frontend/issues/146).

## Admin console run

With the dedicated admin credentials, Playwright login reached `/admin` and
the following read-only pages hydrated without browser errors: dashboard,
workspaces, users, sender IDs, providers, pricing, and audit. The correct
notifications route is `/admin/alerts` (not `/admin/notifications`); it loaded
the notification inbox, filters, settings link, and workspace-created entries.
The initially probed `/admin/notifications` 404 was therefore a test-route
mistake, not a product defect.

A bounded navigation pass then loaded all 18 admin targets individually, using
`commit` navigation and a 3-second per-route timeout. Every target reached its
expected admin shell or page content, with no `This page does not exist` result:
dashboard, countries, carriers, providers, routes, numbers, workspaces, users,
sender IDs, compliance, pricing, payments, settlement, incidents, alerts,
legal, audit, and admins.

## Deterministic frontend control tests

The frontend control tests were run independently of the live browser session:

- notification inbox, admin alerts, notification bell, and customer-gap
  controls: 15/15 passing;
- compose capability gates and phone-input behavior: 61/61 passing.

These cover component and state behavior. Issue #146 remains a browser-level
affordance problem where the visible Send button is not disabled for an invalid
recipient, despite the underlying phone-input tests passing.
